# dtype 子能力有无 Skill 规划行为对比（精炼版）

## 概述

本轮测试关注 Agent 面对 dtype 任务时的规划行为，主要观察职责判断、读取顺序、仓库事实核验、未知契约处理等能力。

## 测试样例精炼总结

---

### D1：只有产品名称的新格式（`nova-float`）

**测试场景**：只有产品名称，目标契约基本未知
#### 原始测试语

> AMCT 准备支持一种暂定名为 `nova-float` 的新量化格式，在进行编码。目前只有这个产品名称，产品侧还没有给出更详细的格式说明。请基于当前仓库给出接入前的任务规划。本次只做只读分析，不修改代码，不执行测试或量化。

#### 无Skill回答要点

**有效行为**：
- 发现名字带来的三个可立即决策项：模块名、算子标识、注册键
- 发现两处静默错误：`llm_deploy.py:58` 的 `startswith("mx")` 和 `deepseekv4.py:257` 的 `else` 兜底
- 识别出 `is_mx` 布尔量把"是否浮点类型"与"是否32 block缩放"绑在一起的问题
- 给出格式名集中化、is_mx解耦、白名单改为注册表派生等建议

**主要偏差**：
- 直接假定"新增dtype类"，未先判断是否真需要新dtype
- 在数值语义未冻结时就确定文件名、注册键和重构计划
- 把搜索命中的硬编码分支倾向性地列为必改面

#### 有Skill回答要点

**核心改进**：
- 先过"既有语义复用门"，判断 `nova-float` 是否真是新dtype
- 交付"一个前置裁决 + 三条分支"而非单一计划
- 三条分支：A)语义已覆盖→零改动/别名；B)classic等价→迁入new-path；C)新语义→按playbook分层实施
- 九个消费面全部标 `pending`，无推荐默认

**关键差异**：
- 起点假设：无Skill直接假定新增 vs 有Skill先问"这是不是新dtype"
- 交付形态：单一线性计划 vs 三条件分支 + 封闭阻塞输入
- 契约处理：默认适用范围 vs 全部标pending

**对比判断**：明显改善；状态机方向有效

### D2：带有错误复用暗示的方案评审（`orbit4`）

**测试场景**：用户建议"复制4bit实现即可自动接通"


#### 原始测试语

> 有人建议新增 `orbit4` dtype 时直接复制仓库现有的一套 4 bit 实现，只替换注册名，这样 CLI 和部署应该就能自动支持。请评审这个方案并给出下一步规划。本次只读，不修改任何文件。

#### 无Skill回答要点

**有效行为**：
- 正确否决"CLI和部署自动支持"，指出两处硬编码白名单
- 发现本仓有两套互不兼容的4bit实现（int的4bit vs mxfp的4bit）
- 指出"改名不产生新格式"的根本问题
- 识别出复制会带进的隐藏耦合（2D假设、block_size、packing约束等）

**主要偏差**：
- 仍建议先建骨架和做跨层去硬编码重构
- 把搜索命中的algorithm、model分支列为必改面

#### 有Skill回答要点

**核心改进**：
- 直接否决三个前提：没有独立4bit文件可复制、CLI不自动支持、deploy静默错分
- 引入"复用门"：先比较数值语义，判断是否真需要新dtype
- 消费面逐项核验：registry、CLI、bit policy、weight/activation quantizer、deploy
- 交付条件式规划：根据数值语义等价性走不同分支

**关键差异**：
- 起点假设：接受"复制并改名" vs 先比较数值语义和实际消费入口
- 交付形态：先建骨架和重构 vs 区分别名、复用和新增
- 证据等级：混淆"注册成功"与"下游已支持"

**对比判断**：明显改善；复用门和消费面门有效

### D3：部分契约已经冻结（`quark4`）

**测试场景**：role与bit已知（weight-only, 4bit），其余契约未知

#### 原始测试语

> 计划在 AMCT 中增加 `quark4`。目前已确认它只用于权重、固定 4 bit，并且不量化 activation 和 cache；数值编码、量化粒度以及是否进入部署导出仍未确定。请给出实现前规划。本次只读，不修改代码或运行测试。

#### 无Skill回答要点

**有效行为**：
- 识别出"固定4bit"与`ActivationQuantizer`无条件构造的冲突
- 发现bit policy要求w_bits/a_bits必须成对出现
- 给出dtype骨架、CLI放行、weight-only契约测试等建议

**主要偏差**：
- 仍预设新增文件、CLI和可选NPU路径
- 根据命名惯例建议把注册名从`quark4`改成`quark`，证据不足

#### 有Skill回答要点

**核心改进**：
- 纠正三个必须先纠正的实现前提：
  1. "不量化activation"不能由dtype类拒绝is_act实现
  2. "固定4bit"不代表类内可以假定bits==4
  3. 名字里带bit数与现有架构不一致
- 消费面状态：已知项正常采用，未知项保持pending
- 补出`is_act=True`构造和16bit直通约束

**关键差异**：
- 契约处理：预设新增 vs 三个必须纠正的实现前提
- 落点选择：直接给文件名 vs 只列候选锚点
- 命名建议：自动改名 vs 建议但最终由用户定

**对比判断**：有改善；存在注册名默认选择过早的问题

### D4：只有dtype类和注册的"已完成"方案（`luma`）

**测试场景**：已有dtype类、注册和数值单测，声称接入完成

#### 原始测试语

#### 无Skill回答要点

**有效行为**：
- 正确否决"完成"结论，指出CLI拒收、deploy静默跳过、导出元数据标错
- 发现4个硬阻塞：register_dtype()的import链、CLI白名单、deploy白名单、is_mx布尔量
- 给出后续检查计划：可达性验证、分支穷举、交付面缺口

**主要偏差**：
- 混入未由题面触发的NPU和较大范围清单
- 部分检查计划过于详细

#### 有Skill回答要点

**关键差异**：
- 起点假设：接受"已完成" vs 从定义和注册继续反查真实消费者
- 交付形态：硬阻塞+条件阻塞+检查计划 vs 当前事实/目标契约表反证
- 契约处理：默认适用范围 vs 九个消费面全部标pending

**对比判断**：有改善；CLI是否立即公开仍有状态不一致

**对比判断**：明显改善；跨Skill职责边界有效

## 综合分析

### 两种模式的核心差异

| 维度 | 无Skill模式 | 有Skill模式 |
| --- | --- | --- |
| **起点假设** | 默认"新增dtype" | 先问"是否需要新增" |
| **契约处理** | 默认适用范围 | 全部标pending，无推荐默认 |
| **交付形态** | 单一线性计划 | 条件分支 + 封闭阻塞输入 |
| **落点选择** | 给出唯一文件名 | 只列候选锚点 |
| **证据等级** | 混淆源码存在与集成闭环 | 区分不同级别证据 |

### 主要改进点

1. **状态机方向**：从"如何新增dtype"前移到"是否需要新增，以及哪些目标契约已经冻结"
2. **复用门**：先比较数值语义，判断是否真需要新dtype
3. **消费面检查**：稳定暴露"类存在、注册成功，但CLI/quantizer/deploy未接通"的问题
4. **职责边界**：Python侧契约review与NPU kernel/schema/Meta/build职责分离

### 仍存在的问题

1. 输出仍然偏长，读取和事实枚举较多
2. 部分样例（D3、D4）存在契约被提前收口的问题
3. 不能证明信息充分时Agent会及时结束提问和检查

## 附录：统一行为评分标准

| 维度 | 2分判据 |
| --- | --- |
| 职责与主路径 | 选择dtype主场景；涉及外部职责时只在真实交界成立后分流 |
| 读取顺序 | 先读主规则和少量直接锚点，再由未解决契约驱动扩张 |
| 仓库事实 | 注册、CLI、bit policy、quantizer或deploy结论有当前源码/caller/测试证据 |
| 契约控制 | 已知项正常采用；未知项不被名称、参考实现或后续叙述静默冻结 |
| 条件式规划 | 分支与缺失契约一一对应，不把候选落点写成唯一实现 |
| 消费面核验 | 不用"新增类/已注册"代替实际quantizer、CLI或deploy消费证据 |
| 上下文收敛 | 达到任务所需证据后停止；超出默认预算前能说明具体未解决契约 |
| 交付可信度 | 区分源码、单测、集成和真实环境证据，不声称执行未做的动作 |

**最高分限制**：使用当前仓库不存在的CLI参数、把没有caller的helper当成活跃路径、在没有新证据时把未知目标契约改成确定方案、选择错误代码体系、声称已经运行实际未执行的测试时，该题最高记8/16。
