# AMCT Coder

AMCT 源码级编码、实现规划、行为诊断与 review 的路由入口。默认中文；修改代码前简述主落点层和允许改动范围。

## 轻级直达卡

**①~④ 全中才走快速路径**（此处是四条判据的唯一出处，分级表引用它）：① 动手前能列出全部待改文件（诊断/review 类视为满足；**需先查调用链才能定位的不入轻级**）② 单一落点层 ③ 不触 public 契约 ④ 不命中门禁对象（新 dtype / 算法 / solver / granularity、复合 unit、skip/partial result）。
**全中 + 普通修复（行为实现 bug）** → 就地四步直达，**不必读分级表、process-rules、repo-map、walkthrough、主手册，以及本文件分界线之后的任何节**：定位（rg 符号 → 读目标函数与直接调用方，通常 ≤3 个锚点即停）→ 改（按 [coding-rules](references/coding-rules.md) 改动类型对应节，不整读）→ 验（按 [validation.md](references/validation.md)「按变更类型选验证」选最小验证，失败按其「验证失败的处理」分类处置）→ 交付（按下方「交付格式」，不适用项写 `n/a`）。**全中 + 诊断/review/规划** → 仍判轻级，读一个主手册的公共节+命中节。**纯规范合规检查**（不落盘代码、无行为面）→ 免读主手册，只读 coding-rules 相关节。**任一条不中，或属新功能/跨模块/动契约** → 标准级或重级，走下方完整流程。
判据有疑（要先查才能定）→ 直接判标准级；分级判断超过一次源码定位的成本时就已选错级别。豁免只免读取、不免约束：①~④、命中手册的 BLOCKER 与全局 BLOCKER 照常适用；执行中越界即按「单向升级」升标准级补齐，资料复用，分级写进交付说明。四步没覆盖的情形按「场景 Reference 导航」查单个 reference，不整读导航表。

## 核心流程（职责归属判定后、留在本 skill 的任务执行）

```text
0. 分级 -> 1. 判职责归属 -> 2. 边界（轻级跳过）+ 选主手册 -> 3. 锚点定位并执行 -> 4. 验证并按分级格式交付
```

### 各级都要做

**职责归属**（优先级从高到低）：① 用户明确指定的 skill 按用户目标执行；② 否则按当前会话已发现 skill 的 `name + description` 判断，任务实质已被更专门 skill 覆盖时直接加载并遵循它，不预读本 skill 的 repo-map/手册，也不要只说「应使用某 skill」就结束；③ 列表疑似不完整（插件未加载、skill 未注册）时，以仓库 `.agents/skills/` 各 skill 目录的 frontmatter description 补充核对；④ 同名冲突或仍无法确认时按本 skill 流程处理并在交付说明点明可能的职责重叠。实现代码 vs 运行命令按动作判断，不按关键词；混合任务按职责拆分，本 skill 收口源码级部分和共享契约。

**事实纪律**（对每个待核实契约按序，第一个「是」停）：

- Q1 能由源码/测试/调用方查明？→ 查完再判定，不问用户；先查再建。
- Q2 是不影响公开契约的局部选择？→ 自行决定并点明（默认值改变用户可见行为不属此类）。
- Q3 查不到时不同答案产出不兼容实现？→ 编码类按「契约缺失形态」先问用户（封闭选项、一次问完、无依据不伪造推荐）；规划类保留条件分支；否则按最合理解释继续并标注假设。

全程标记纪律：未冻结契约只列候选锚点、不发明命名；前后文不得静默改写待确认项；区分「函数存在」与「调用链接通」；源码与用户描述冲突时以源码为准；未排查完整数据链不用「唯一根因」。

**单向升级**：轻级执行中越界即升标准级补齐（边界声明回 process-rules「仓库边界」，已写代码按新级别的验证要求重验），资料复用；分级写进最终说明。升级即离开直达卡的四步路径，且需回读下方分界线之后的「分级」节。

**验证证据分级**：源码存在 < 单测覆盖 < 集成闭环 < 真实环境验证；不得用低级证据替代高级结论，缺硬件/权重时明确写出。改完按 [validation.md](references/validation.md) 选最小验证；只读任务核对既有证据、不改快照（差异写进交付说明）。

**交付格式**（唯一出处；任何 reference 只可引用、不得复制此清单）：开头一句话标分级；只汇总实际执行过的动作，不补写未执行步骤——改了代码（主场景、改动文件、事实与待确认项、复用抽象、已跑/未跑验证及阻塞原因、是否触及敏感层、repo-map/docs 是否需更新）/ 没改代码（边界、事实、方案、已核对与缺失证据）/ 纯规范检查（检查项、发现、证据）。敏感层指 workflow、solver、quant module、public API、ops build，触及即单独点明（影响面超出本次落点）。不适用的项写 `n/a`，不整项省略。

**BLOCKER 只停错误方案不停任务**：替代路径明确且在用户目标内就直接继续；信息缺失先推进不依赖它的部分。

### 以下仅标准级及以上读取（轻级到此为止，直达卡命中者不必往下翻）

#### 规则执行层级

上方「各级都要做」即第一层，每个任务都执行。另两层按判据命中才激活：

- **仅标准级及以上执行**：边界声明与 repo-map 读取（按领域分档）、契约状态模型/门禁表填写（重级）、跨 producer/consumer 双端核对（重级）。
- **仅异常路径执行**：Q3 与契约询问（查不到且答案影响实现才触发）、BLOCKER 处置（撞到才用）、快照冲突修正（核对命令与断言不符才改）。

#### 分级

轻级判据 ①~④ 见首段「轻级直达卡」（唯一出处），本表只列标准级与重级的追加判据和各级流程。

| 级别 | 判据 | 流程 |
| --- | --- | --- |
| 轻 | 直达卡 ①~④ 全中 | 跳过边界声明；按直达卡决定是否读主手册（读则公共节+命中节）+ 编码按改动类型读 [coding-rules](references/coding-rules.md) 对应节（Python 改动读风格/日志/健壮性/测试节，C/C++ 加读「代码风格与版权」内的 C/C++ 条——本仓不单设 C++ 节；不整读）→ 改 → 最小验证 |
| 标准 | 默认 | 完整流程：职责归属 → 边界声明 → 主手册与锚点定位 → 修改/诊断 → 验证与交付（细则见 [process-rules.md](references/process-rules.md)） |
| 重 | ① 命中直达卡判据④的门禁对象清单 ② 跨契约（保存/加载、CLI/registry、dtype/deploy 等两端）③ 触 public 契约 | 完整流程 + 门禁表/状态模型逐项填写 + 双端验证（按下方「重级的比例原则」只填触及项） |

**主手册豁免的依据**（操作性规则见首段直达卡，此处只讲为什么）：主手册回答的是「落点在哪一层、是否越层、上下游契约是什么」。直达卡命中的普通修复与纯规范合规检查，由判据本身已经回答了这三点——前者入口条件已给定待改文件、单一落点、不动契约，后者不落盘代码、无行为面——故免读主手册，直接读源码定位。其余轻级仍读一个主手册。豁免只免读取、不免约束；执行中发现落点层或契约存疑，即按单向升级回主手册补齐。

**重级的比例原则**：重级的重量来自「跨端一致性有风险」，不来自「改动行数多」。门禁表与契约状态模型只填本次实际触及的行，未触及的消费面写 `n/a` 并一句话说明为何不涉及，不逐项论证；双端验证只跑真实受影响的两端。单点 public 契约变更（改一个 CLI 默认值、改一处 choices、改一个导出字段名）判重级但只需三步：producer/consumer 两端核对 + 兼容性影响说明 + 对应 parser/导出测试，不要求填完整契约状态模型。

**三步简化不适用于命中门禁对象的变更**：门禁对象的风险是「注册成功不等于可用」，单点契约变更的风险是「用户可见行为变了」，两者不同源——前者不能靠两端核对消掉，仍需门禁表逐项过。同时命中时按门禁对象处理：例如改 `--granularity` 默认值虽只是一行 CLI 改动，但 granularity 属门禁对象，不享简化。

分级示例（校准用；新任务仿照判据路径，不套用结论）：

| 请求 | 级别 | 判据路径 |
| --- | --- | --- |
| 「修一下这个函数的报错日志措辞」 | 轻 | 文件可列出、单一落点、不改行为 |
| 「把某 CLI 参数默认值从 A 改成 B」 | 重 | 默认值改变用户可见行为 → 触 public 契约（也命中事实纪律 Q2 的例外）；不属门禁对象时按「重级的比例原则」只需两端核对 + 兼容性说明，属门禁对象（如 `--granularity`）则不享简化 |
| 「新增一个 dtype 注册到 `--quant_dtype`」 | 重 | 命中门禁对象（新 dtype）+ CLI choices 是 public 契约 |
| 「已有 adapter 的 forward 有个 bug，输出和 float 不等价」 | 标准 | 文件可列出但行为正确性需沿捕获→forward→wrapper 链核验，前置资料不足轻级 |
| 「只检查这次改动是否符合代码风格/版权」 | 轻 | 不落盘代码、无行为面；读 coding-rules 的相关规范节即可，无需主手册 |

## 术语（本 skill 自造词，唯一出处）

各 reference 直接使用这些词、不再解释。读本页遇到不明术语回这里查。

| 术语 | 含义 |
| --- | --- |
| 落点层 | 改动应落在哪一层：CLI / workflow / solver / quant module / dtype / algorithm / adapter / deploy / public API。落点错层是本仓最主要的错误来源，分级判据②即约束它。 |
| 主手册 | 本次任务唯一的主场景 reference（导航表「主场景」行）。一个任务只选一个，第二个只能作辅助；豁免情形见首段直达卡。 |
| 门禁对象 | 命中即强制升重级的对象：新 dtype / 新算法 / 新 solver / 新 granularity、复合 unit、skip/partial result。共同点是「注册成功不等于可用」。 |
| 门禁表 / 契约状态模型 | 重级任务逐项填写的表，把「当前仓库事实」与「目标契约」分账，未冻结项标 `pending`。填法受「重级的比例原则」约束。 |
| 快照 / 核对命令 | 手册里对当前源码状态的断言，附一条可执行的 `rg`/`grep` 命令。冲突时以命令结果为准，不以文档为准；引用快照事实作落点依据前先跑它。 |
| 事实纪律 Q1/Q2/Q3 | 待核实契约的消歧顺序：源码能查就查（Q1）→ 不影响公开契约的局部选择自行决定（Q2）→ 查不到且不同答案产出不兼容实现才问用户（Q3）。第一个「是」即停。 |
| 契约缺失形态 | Q3 触发后向用户提问的规定形态：封闭选项、一次问完、无依据不伪造推荐。 |
| 双端验证 | producer 与 consumer 两侧都验（保存侧与回载侧、CLI 侧与 registry 侧）。只验一侧会漏掉「静态可写、运行不可读」。 |
| 消费面 | 一个能力的下游接入点集合（registry / CLI / bit policy / quantizer / deploy / algorithm / model 分支）。新增能力要逐面收口，不能只证明定义存在。 |
| 敏感层 | 改动影响面超出本次落点的层，交付说明须单独点明；枚举以「交付格式」为准。 |
| BLOCKER | 手册中标注的硬约束。语义是「这个方案错了」，不是「任务停止」：替代路径明确且在用户目标内就直接继续。 |
| 收束 | 停止扩张上下文、开始交付的时刻。判据是停止条件（见 process-rules「渐进披露与读取预算」），不是读了多少资料。 |
