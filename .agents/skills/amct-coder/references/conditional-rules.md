# 条件细则：conditional-rules

## 仓库边界

repo-map 读取范围按任务领域分档，repo-map 自述的适用范围（新模型适配与 PTQ 流程定位）高于全量默认。需求已把改动面点名到具体文件或函数——只落一处、不触跨端约定、不波及 workflow、solver、quant module、public API、ops build——不分档读取，直接进入定位；结论一旦牵扯其它位置、实现行为或调用链即作废，回到分档补齐资料。

| 任务领域 | repo-map 读取范围 |
| --- | --- |
| LLM CLI/workflow、solver、模型适配（含 review 与局部修复） | 「分层边界」全量——这些层的跨端约定是 repo-map 的覆盖核心 |
| dtype/quant module、deploy、public API、packaging | 只读改动位置对应的 section——repo-map 主要覆盖 LLM 主链，这些领域按需定位 |

读完按候选位置的主要入口和关键符号抽查源码，确认 map 与当前实现一致：map 只用来定位该看哪几层、哪条链，修改位置和行为一律由源码定。

## 跨端约定核对的做法

决定跨端约定核对做到多重：跨端约定状态表填多少、两端核对跑哪两端。

**重点核对对象**是新 dtype / 算法 / solver / granularity、复合 unit、skip/partial result 这几类——注册成功不等于真能用，必须核对到实际消费入口。

### 比例原则

跨端约定状态表只填本次实际触及的行，未触及的下游接入点写 `n/a` 并一句话说明为何不涉及，不逐项论证。单点对外接口变更（改一个 CLI 默认值、改一处 choices、改一个导出字段名）只需三步：producer/consumer 两端核对 + 兼容性影响说明 + 对应 parser/导出测试，不要求填完整跨端约定状态表。

**三步简化不适用于命中重点核对对象的变更**：这类对象的风险是「注册成功不等于可用」，靠两端核对消不掉，仍需跨端约定状态表逐项过。同时命中时按重点核对对象处理，例如改 `--granularity` 默认值虽只是一行 CLI 改动。

## 当前事实与核对命令纪律

核对命令搜不到锚定符号本身就是过期信号。命令失败但源码行为与断言语义仍一致时，以语义为准，不算「当前事实」过期，在交付说明里点明；行为变了才算过期。资料（repo-map 与手册）与源码冲突时以源码为准，不改资料，把差异写进交付说明的发现项。
