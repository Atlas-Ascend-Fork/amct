# 条件细则：conditional-rules

## 仓库边界

要不要读 repo-map、要不要做边界声明，看**边界是否已经确定**，不看任务叫什么名字：

- **改动面已被题面唯一钉死**——点名了文件或函数、只落一处、不触跨层约定、不波及共用架构层（定义见 [SKILL.md「交付格式」](../SKILL.md#交付格式)）——就地声明边界，跳过分档读取，直接进入定位。典型形态是「把这个函数的报错文案改清楚」。
- **改动面还没钉死**——落点、调用链或影响面还需查证（实际编码、实现规划、行为诊断、架构或代码行为 review）——按分档读取并走下面的三步声明。

就地声明只在边界确实钉死时成立：一旦结论牵扯其它落点、实现行为、调用链或上下游约定即作废，回到分档补齐资料，不拿最初那句话当边界用到底。

分档是为了把无关层挡在判据之外，不只是省 token：读进来的每一层都会被当成本次改动的边界依据。repo-map 读取范围按任务领域分档，repo-map 自述的适用范围（新模型适配与 PTQ 流程定位）高于全量默认：

| 任务领域 | repo-map 读取范围 |
| --- | --- |
| LLM CLI/workflow、solver、模型适配（含 review 与局部修复） | 「分层边界」全量——这些层的跨层约定是 repo-map 的覆盖核心 |
| dtype/quant module、deploy、public API、packaging | 只读落点对应的 section——repo-map 主要覆盖 LLM 主链，这些领域按需定位 |
| 纯规范合规检查（只查代码风格、版权或贡献门槛，不落盘代码） | 不读取；无落点可声明，本节跳过 |

边界声明三步：

1. 按上表读取对应 repo-map 范围。
2. 按候选落点的主要入口和关键符号抽查直接相关源码，确认 map 与当前实现一致。
3. 在内部形成边界声明：主要架构层、允许范围、禁止事项、必要辅助层。

repo-map 是稳定架构约定，源码是当前行为事实，只读不改：map 只用来定位该看哪几层、哪条链，落点和行为一律由源码定。两者冲突时以源码为准，先判断源码是否越层；map 过期不改 map，把差异写进交付说明的发现项。

## 跨端约定核对的做法

决定跨端约定核对做到多重：跨端约定状态表填多少、两端核对跑哪两端。

**门禁对象**是新 dtype / 算法 / solver / granularity、复合 unit、skip/partial result 这几类——注册成功不等于真能用，必须核对到实际消费入口。

### 比例原则

核对做到多重，看「两端对得上有没有风险」，不看「改动行数多」。跨端约定状态表只填本次实际触及的行，未触及的下游接入点写 `n/a` 并一句话说明为何不涉及，不逐项论证；两端核对只跑真实受影响的两端。单点对外接口变更（改一个 CLI 默认值、改一处 choices、改一个导出字段名）只动到对外接口这一条，只需三步：producer/consumer 两端核对 + 兼容性影响说明 + 对应 parser/导出测试，不要求填完整跨端约定状态表。

**三步简化不适用于命中门禁对象的变更**：门禁对象的风险是「注册成功不等于可用」，单点约定变更的风险是「用户可见行为变了」，两者不同源——前者不能靠两端核对消掉，仍需跨端约定状态表逐项过。同时命中时按门禁对象处理：例如改 `--granularity` 默认值虽只是一行 CLI 改动，但 granularity 属门禁对象，不享简化。

### 校准示例

校准用；新任务仿照「理由」列的判断路径，不套用结论。第二列给出要不要加跨端约定核对。

| 请求 | 跨端约定核对 | 理由 |
| --- | --- | --- |
| 「修一下这个函数的报错日志措辞」 | 不加 | 改动面已由题面钉死，就地声明、不整读 repo-map 分档；不改行为、不动跨端约定、落在单一非共用架构层 |
| 「把某 CLI 参数默认值从 A 改成 B」 | 加 | 默认值改变用户可见行为 → 动到对外接口（因此不是可以自己定的局部选择）；不属门禁对象时按「比例原则」只需两端核对 + 兼容性说明，属门禁对象（如 `--granularity`）则不享简化 |
| 「新增一个 dtype 注册到 `--quant_dtype`」 | 加 | 命中门禁对象（新 dtype）+ CLI choices 属对外接口 |
| 「已有 adapter 的 forward 有个 bug，输出和 float 不等价」 | 不加 | 行为正确性需沿捕获→forward→wrapper 链核验，但不触跨端约定 |
| 「只检查这次改动是否符合代码风格/版权」 | 不加 | 不落盘代码、无行为面；读 coding-rules 的相关规范节即可，无需主手册 |

## 跨端约定缺失的处理形态

要核实的跨端约定查不到、且不同答案会产出不兼容的实现时，按本节处理。

能查到就查完：越层落点、错误复用和禁止项由源码、注册入口、活跃调用链和测试直接否决，不为已有答案的问题询问用户。

查不出来时先完成不依赖该答案的部分，不要让一个待确认项挂住整个任务。剩余部分按交付物区分：

- **只读规划**：条件分支本身就是交付物。列出各分支的前提、落点差异和验证差异，不必先冻结跨端约定。
- **实际编码**：关键约定未冻结且不同答案产出不兼容实现时，直接询问用户，不写投机实现。按错误假设写出的完整版本返工成本高于提问，且容易把假设固化成事实。

询问遵循以下形态：

- 收敛成封闭选项并说明各选项影响面，不做开放式提问。只有源码惯例、兼容性或实现成本存在可引用证据时才给推荐项；没有依据时明确“无默认推荐”，不伪造偏好。
- 一次问完本轮全部阻塞项，不逐条追问。
- 拿不到答复时，只读规划保留条件分支；已有证据支持推荐项时可以沿推荐分支展开并标注未经确认，没有推荐依据时不替用户选择。实际编码停在约定确认前，只交付已完成部分和待确认约定清单，不落盘投机代码。

## 快照与核对命令纪律

要把手册里的「当前接通事实」「主链状态」等快照节当落点依据，或核对命令与断言不符时，按本节判。

各手册的快照节附有核对命令（「快照」指手册对当前源码状态的断言，不是测试里的张量快照 `snapshot = x.clone()`）：作为落点依据前先执行对应命令，结果与断言冲突时以命令结果为准；命令搜不到锚定符号本身就是过期信号。命令失败但源码行为与断言语义仍一致时，以语义为准，不算快照过期，在交付说明里点明。发现快照与源码不符时不改手册，把差异写进交付说明的发现项。
