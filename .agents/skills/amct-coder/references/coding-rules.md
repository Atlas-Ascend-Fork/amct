# 编码规范：coding-rules

本文件只约束 Python 代码规范（仓级条目如「依赖与放置位置」不分语言）。

## 代码风格与版权

- 遵循 PEP8，使用 Ruff 检查和格式化。
- 提交前运行 pre-commit（未安装时按 [validation.md](validation.md#最小静态验证) 的处理：报告未执行原因，不主动安装）。
- 新增文件**必须**包含 Apache 2.0 版权头（AGENTS.md「许可证」要求，仓库规范层面强制）；版权头的具体格式按目录内既有文件的组织方式。`# -*- coding: UTF-8 -*-` 编码声明不强制，以同目录多数文件为准。修改现有文件时不得删除或破坏版权头。注意区分：OAT 检查的 policy 规则（`may`）与 pre-commit 未强制，是检查工具的宽容度，不改变仓库规范要求——新增文件省略版权头应视为违规，即使工具不报错。
- 代码标识符与错误信息用英文；用户可见文档与注释遵循仓内既有语言习惯。

## 日志与错误处理

- 使用项目统一日志打印接口，禁止自定义 `print` 输出。
- 错误描述完整：异常文案须指明参数名、实际值与期望约束；不用 "Inner Error" 等模糊措辞做错误描述。
- 数值类日志带度量单位（bit/MB/ms 等）。

## 健壮性边界

- fail-fast：配置/前置条件不满足时在最上游抛明确异常，不进入流程后才失败；不得用“缺输入 → 静默跳过”之类降级掩盖错误——静默跳过会产出看似成功、实际降质的模型。
- 修 bug 控制在 issue 指定范围内，不顺手扩展到其它路径；范围外问题另开 issue。
- 改动兼容性要核对仓内声明支持的环境区间，不只看当前开发环境。
- 向后兼容：既有 public API 的签名与语义、CLI 参数名/choices/默认值不得无声变化；默认值变更改变用户可见行为时，按新功能处理（见「贡献门槛对编码的约束」），并在交付说明中单独点明。
- 随机性可复现：新引入随机性的路径（初始化、采样、数据 shuffle）必须提供可控种子入口并接入既有传参链；不得在无种子控制的路径上新增随机行为。
- 资源清理：新建的临时文件/目录、句柄和 device 内存要在失败路径上也可释放。

## 依赖与放置位置

- 新增第三方依赖按用途落对入口：**运行依赖**进 `requirements.txt`（当前运行依赖的唯一安装入口，README 指引用它安装）；**构建依赖**仅 setuptools/wheel，进 `pyproject.toml` 的 `[build-system]`（该文件当前无 `[project]` 依赖表，不承担运行依赖）。并核对仓内声明支持的环境区间内该依赖可得；只在部分环境可得的依赖走可选依赖路径（`setup.py` 的 `extras_require`），不得静默变成硬依赖。不因新增依赖改变现有打包机制（如把 requirements.txt 迁入 pyproject）。
- 泛化性未经充分验证的新特性落 `experimental` 目录（如 `amct_pytorch/experimental`），按其 src/doc/README 结构组织；进入正式目录需要先补验证证据。
- 涉及算子仓的新增或修改，先在算子仓合入对应变更，再推进本仓特性合入；本仓不携带算子侧的替代实现。

## 测试编写

- 数值断言的测试必须确定性：固定随机种子（仓库 conftest 已有全局 deterministic fixture，模块内额外随机源自行固定），不依赖执行顺序。
- 按资源需求打 pytest marker：纯 CPU 快速用例 `cpu`（默认档）、需要 NPU 的 `npu`、耗时用例 `slow`；marker 在 `pyproject.toml` 注册，不自造新 marker 名。
- 模型、硬件、外部服务依赖用 mock 隔离，测试不因缺 NPU/CANN/权重而报错，只允许显式 skip；skip 条件要说明缺什么。

## 构建与环境门槛

以 [README.md 快速开始](../../../../README.md) 和 [docs/zh/build.md](../../../../docs/zh/build.md) 为准；验证声明的证据等级（缺 CANN/NPU/权重时最多报告到什么级别）见 [validation.md](validation.md#证据等级)。

## 贡献门槛对编码的约束

贡献流程的完整规范以 [CONTRIBUTING.md](../../../../CONTRIBUTING.md) 为准。

对编码任务唯一相关的约束：**新功能或接口变更必须先通过 Issue 讨论达成共识，再提交 PR**；简单 bug 修复可以直接提交。因此拿到新功能或接口变更请求时，先确认用户是否已有共识 Issue——用户只授权本地编码时，说明该门槛即可。
