# 流程细则：process-rules

本文件是 [SKILL.md](../SKILL.md) 核心流程的完整展开，**不引入新规则**——与 SKILL.md 冲突时以 SKILL.md 为准（它是唯一规则来源），并在交付说明中报告冲突，不就地改文档；发现 process-rules 自身与 SKILL.md 不一致时按 [validation.md](validation.md#按变更类型选验证) 的 skill 修改流程修。轻级任务无需读取；标准级及以上任务按 SKILL.md 末表的触发情形读取对应节。

## 仓库边界

实际编码、实现规划、行为诊断、架构或代码行为 review 都要先声明边界；轻级任务按「任务分级」跳过本节，只检查代码风格、版权或贡献门槛的纯规范合规 review 也默认跳过。轻级任务执行中升级回标准/重级时，必须回到本节补齐。一旦结论涉及实现行为、架构落点、调用链或上下游契约，就不再是纯合规检查，同样必须回到本节补齐资料。

读取范围按任务领域分档，repo-map 自述的适用范围（新模型适配与 PTQ 流程定位）高于全量默认：

| 任务领域 | repo-map 读取范围 |
| --- | --- |
| LLM CLI/workflow、solver、模型适配（含 review 与局部修复） | 「分层边界」+「更新规则」全量——这些层的跨层契约是 repo-map 的覆盖核心 |
| dtype/quant module、deploy、public API、packaging | 只读落点对应的 section +「更新规则」——repo-map 主要覆盖 LLM 主链，这些领域按需定位 |
| 纯规范合规检查 | 不读取 |

边界声明三步：

1. 按上表读取对应 repo-map 范围。
2. 按候选落点的主要入口和关键符号抽查直接相关源码，确认 map 与当前实现一致。
3. 在内部形成边界声明：主落点层、允许范围、禁止事项、必要辅助层、是否需要写回 repo-map。

repo-map 是稳定架构契约，源码是当前行为事实。repo-map 前置读取不代表默认写回，写回判据以已读的 repo-map「更新规则」为准。两者冲突时，先判断源码是否越层；源码代表预期的新边界或核心流程时，把 repo-map 修正纳入本次任务。

## 职责归属细则

先根据用户要执行的动作和当前会话已发现 skill 的 `name + description` 判断职责，不维护外部 skill 的完整副本。任务实质已被更专门 skill 覆盖时，直接加载并遵循该 skill，后续加载和交付由它决定。

当前会话的 skill 列表可能不完整（插件未加载、skill 未注册等）：任务疑似属于专门职责但已发现列表中没有对应项时，以仓库 `.agents/skills/` 下可用 skill 目录的 frontmatter description 和用户明确指定的 skill 作为补充核对来源，确认存在更专门 skill 后按其执行。仍无法确认时按 amct-coder 流程处理，并在交付说明中点明可能存在的职责重叠。

修改 eval/deploy 等**实现代码**仍属于 amct-coder；运行命令拿结果或生成交付产物属于操作流程。不要只看 `eval`、`deploy`、`attention`、`校准` 等关键词，必须结合动作、代码体系和被修改契约判断。用户明确指定 skill 或动作时，按用户目标执行；若涉及多个职责，加载相关专门 skill 协作，并由本 skill 负责源码级部分和共享契约收口。

混合任务按职责归属拆分：本 skill 处理辅助编码范围内的部分，其余部分进入对应 skill；全部完成后统一检查契约并汇总。

### 区分实现与落点 review

- 用户要求**新增或结构性实现**属于专门 skill 的职责时，第一步直接进入对应 skill。
- 用户要求**评审一个明确文件或拟议方案是否合理**时，由 amct-coder 审查当前落点：只读取该落点所需的 repo-map 切片、一个主操作手册以及由主要入口和关键符号定位到的源码，判断是否越层或错误复用；确认正确实现属于外部职责后，再进入对应 skill 继续。
- 用户报告局部 bug 时，先核验现象和根因。若最终需要新增模型结构、NPU kernel 或执行实验，再按核验结果路由；不要只因题面出现模型名、算子名或 eval 关键词提前改判。

### 契约缺失的处理形态

第一档能查到就查完：越层落点、错误复用和 BLOCKER 由源码、注册入口、活跃调用链和测试直接否决，不为已有答案的问题询问用户。

查不出来时先完成不依赖该答案的部分，不要让一个待确认项挂住整个任务。剩余部分按交付物区分：

- **只读规划**：条件分支本身就是交付物。列出各分支的前提、落点差异和验证差异，不必先冻结契约。
- **实际编码**：关键契约未冻结且不同答案产出不兼容实现时，直接询问用户，不写投机实现。按错误假设写出的完整版本返工成本高于提问，且容易把假设固化成事实。

询问遵循以下形态：

- 收敛成封闭选项并说明各选项影响面，不做开放式提问。只有源码惯例、兼容性或实现成本存在可引用证据时才给推荐项；没有依据时明确“无默认推荐”，不伪造偏好。
- 一次问完本轮全部阻塞项，不逐条追问。
- 一个待确认项不阻塞整个任务；其余不依赖该答案的部分继续做完。
- 拿不到答复时，只读规划保留条件分支；已有证据支持推荐项时可以沿推荐分支展开并标注未经确认，没有推荐依据时不替用户选择。实际编码停在契约确认前，只交付已完成部分和契约清单，不落盘投机代码。

## Reference 读取

主场景描述只提供粗粒度导航。具体触发、实现定位、执行步骤和 BLOCKER 以对应 reference 为准；不要在导航表继续枚举算法、参数、文件或未来可能出现的全部需求。

多个主场景同时可能命中时，先根据用户动作、目标入口、被修改契约和活跃调用方确定主手册。无法唯一确定时，先搜索公共入口、注册点、调用方和直接测试，再按源码所属层选择主手册；只有确认存在真实跨契约影响时，才把第二个主场景作为辅助手册加载。主手册选择仍依赖尚未冻结的关键契约时，按「契约缺失的处理形态」处理。

命中后按「必读公共节 + 命中场景节」读取主 playbook，不要求整份全文。**必读公共节**：职责边界/上下游依赖（本手册没有该节时读开头的链路图/组件表，判断改动是否越层）、BLOCKER（全局约束不随场景豁免）。**按需节**：执行步骤、门禁表、快照节、自验等只在对应场景或动作命中时读取；诊断类任务可只读目标节（如走查示例的「参数回载诊断」），但该节引用了未读节的概念时先补读被引节。无论读到哪一节，手册都是当前任务的活动规则——不能以「只读了部分」为由豁免其中已适用的约束。实际编码、规划或只读 review 需要核对跨层契约时，可把对应 playbook 作为辅助资料按同样方式读取；不要仅因文件列表相邻而加载。

未命中现有手册时不要强行套入最相近项。先用搜索工具查公共入口、注册点、调用方和直接测试，以 repo-map 判断所属层，并根据相关契约形成任务规划。没有 playbook 兜底时，若源码证据已能确定落点和改动范围即可继续；仅当关键契约仍缺失且不同答案会改变实现时，才按「契约缺失时的处理形态」询问用户。只读规划直接交付条件分支，不额外确认。若该场景形成稳定、重复出现的新代码体系，再更新现有手册或新增 reference。

各场景的详细执行步骤、候选锚点和 BLOCKER 由对应 playbook 定义，不在 SKILL.md 重复。

### 阶段影响检查

阶段只描述 LLM 数据流影响，不决定代码职责归属。仅在修改 LLM CLI/workflow、阶段产物或跨阶段契约时检查；classic、ops 和纯 public API/packaging 标记为“不适用”。

需要逐阶段核对时读取 [llm-cli-dataflow.md 的阶段交接](llm-cli-dataflow.md#二阶段交接)；仅为阶段检查时只读该节。通用能力可能同时影响多个阶段，不要强行选择单阶段；列出需要闭环的受影响阶段即可。

## 渐进披露与读取预算

reference 是任务规则。场景手册通过少量主要入口和关键符号说明实现定位，路径只是当前工作区的提示；失效时沿符号、注册和调用关系重新定位，不维护完整文件清单。验证入口与实现定位分开，测试路径和命令集中在 `validation.md`，场景手册保留覆盖目标；测试文件中的断言不能替代活跃调用链证据。各手册的「当前接通事实」「主链状态」等快照节附有核对命令：作为落点依据前先执行对应命令，结果与断言冲突时以命令结果为准；命令搜不到锚定符号本身就是过期信号。核对命令的维护纪律：**只锚定稳定符号**（函数/类/注册名），预期结果优先用符号存在性或调用方有无（`rg "symbol"` / 反向 grep 无命中），不锚定行号、不锚定函数体内的控制流文本——后者在正常重构（挪代码、改分支结构但不改行为）时会误报过期。误报处理：命令失败但源码行为与断言语义仍一致时，以语义为准更新命令，不算快照过期。快照修正按任务形态区分：实际编码任务顺手更新快照并按 validation.md 跑该节核对命令；只读任务（规划、诊断、review）不改文档，把差异写进最终说明的发现项。按以下层级加载：

1. 只加载「仓库边界」要求的 repo-map 范围和一个主 playbook；各 Reference 的用途和加载时机从 SKILL.md 导航表查询，不另行推导。
2. 用搜索工具定位题目中的符号、调用方和直接测试；首轮通常 2～4 个最相关的源码/测试锚点即够，只读相关定义、调用链和断言切片。这是典型规模提示，不是硬额度；每追加一个锚点前自问是否已满足下方停止条件。
3. 边界或契约仍不清楚时，先扩大同一调用链的源码切片，再按导航表追加必要的辅助 reference；只有真实跨契约影响已经成立时才追加其它主 playbook。
4. 模型结构、checkpoint/config 或模型相关精度异常按 L1 -> L2 -> L3 读取 [casebook](../../../docs/casebook/README.md)；主路径或 map/源码差异仍不清楚时，只补读 repo-map 对应 section。
5. 项目规范和验证规则按导航表的加载时机读取，不把它们提前计入主场景资料。

达到以下条件时停止扩张上下文：仓库边界已确定；活跃调用链或未接通状态已有源码证据；已能区分确认事实、待确认契约和条件式方案；修改面与最小验证范围已经明确。不要为了穷举目录、填满 playbook 文件列表或证明无关分支而继续读取。

典型资料形态是 repo-map 最小切片 + 1 个主 playbook + 首轮 2～4 个源码/测试锚点（编码再加规范）。这些数字只是防预读的规模信号，不是硬额度；硬性收口只有上段停止条件——不因接近数字而停。真实跨契约任务按数据流分批加载，每批重新检查停止条件；扩张时说明触发的冲突或缺失证据。

同一会话处理连续任务时，可以复用已经读取且未变化的资料，但要重新按当前动作做职责判断，不能沿用前一任务的结论。记录本轮新增读取和复用项；不重复读取完整大文件，也不能用旧结论替代当前题设的事实核验。

## 全局 BLOCKER

遇到 BLOCKER 时只停止当前错误方案。替代路径明确、仍在用户目标和已有授权内时直接继续；只有缺少会改变实现方案的关键输入、契约或授权时才询问用户，并按「契约缺失的处理形态」处理。信息缺失不等于 BLOCKER：先推进不依赖该信息的部分，不要把整个任务挂住。

- 不在 CLI、workflow、solver 或通用 quant module 中加入模型专属分支。
- 不在本 skill 内新增或结构性修改模型 adapter/wrapper/attention/MLP/MoE；路由 `model-adapter` skill，回来后只做契约 review。
- 不混用 LLM CLI path `ALGO_REGISTRY` 与 classic `AlgorithmRegistry`。
- 新 dtype 要闭环数值语义、注册、支持位宽/粒度和实际消费入口；只有影响持久化或部署格式时才检查导出/回载。
- 新算法要闭环注册、`targets`、用户选择入口和实际调用链；只有产生可持久化参数时才检查保存/加载。
- 新 public API 要闭环定义、导出/懒加载、兼容性和用户可见测试；仅在安装或使用方式变化时更新 packaging/docs/examples。
- `PtqUnit.kind`、extract 文件命名、PTQ 参数保存/加载、eval/deploy `--algos` 和 deploy binding 必须保持一致。
- 新 NPU 算子实现路由 `amct-ops-dev`；上层调用不得绕过 schema/Meta/import 边界。

落点、越层和上下游边界不明确时，先读 `repo-map.md`（按「仓库边界」的分档范围），再按实际调用关系核对目标层的入口、注册点和直接测试；不要在 workflow、solver 或通用 quant module 中加入模型专属分支。
