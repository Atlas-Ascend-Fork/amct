# infer 对接量化工件 Checklist

这份清单面向推理框架接入方，目标是用最短时间判断：

- 当前量化工件能不能接
- 需要补什么信息
- 是走通用接入，还是只能先做 route-specific 适配

如果需要完整背景，请先看 `amct-quantization-framework-guide.md`。

---

## 1. 接入前先确认边界

推理框架接入时，建议坚持这个边界：

- 上游量化框架负责产出工件和量化方案说明
- infer 负责解释这些工件，并映射成运行时对象

infer 不应该重新承担：

- 量化实验决策
- PTQ 求解
- 上游 Python 逻辑逆向理解

infer 最佳角色是：

- 量化工件解释器
- 高性能 runtime

---

## 2. 最小交付物检查

先确认目录里至少有以下四类交付物：

1. `config.json`
2. `model.safetensors.index.json`
3. `*.safetensors`
4. `deploy_quantization.md`

如果缺任意一类，先不要进入接入实现，先回到上游补齐。

---

## 3. `config.json` 必查项

重点不是所有模型字段，而是量化配置字段是否稳定。

至少要确认：

- `quant_method`
- `format`
- `config_groups`
- `ignore`
- `kv_cache_scheme`，如果模型涉及 cache 量化

还要确认两件事：

- 这些字段是否足够支撑 infer 侧选择加载路径
- 同一类模型的字段语义是否稳定，不会每个模型都换名字

如果这两点做不到，后续接入成本会持续升高。

---

## 4. `safetensors` 必查项

至少要确认：

- 权重索引完整
- shard 路由清晰
- 命名规则稳定

对量化张量，建议优先看清：

- `qweight`
- `weight_scale`
- `weight_bias`，如果有
- 结构类算法附加张量
- cache 相关附加张量

如果 infer 侧无法只靠文件命名和说明文档知道要读什么，说明导出契约仍不够成熟。

---

## 5. `deploy_quantization.md` 必查项

这是 infer 侧最重要的说明文档。

至少应该回答：

1. 当前量化目标映射到 infer 的什么运行对象
2. 每类运行对象需要读取哪些张量
3. 每类张量的 shape / dtype / 广播规则是什么
4. 是否需要 post-load 处理
5. 是否存在结构变换带来的运行时要求
6. 哪些模块允许回退，如何回退

如果这份文档更像实验记录而不是运行规格，infer 侧后续维护会非常吃力。

---

## 6. 运行对象映射检查

infer 接入时，优先把上游 target 映射成稳定的运行对象，而不是绑定模型名字。

优先看是否能归并到：

- `Linear`
- `MoEGMM`
- `KVCache`

如果一个目标无法稳定落入上述对象之一，需要尽早判断：

- 是不是 route-specific 方案
- 是不是需要增加新的运行对象抽象
- 还是应先回到上游重设计量化方案

---

## 7. post-load 检查

很多量化方案真正容易出问题的，不是文件能不能读，而是加载后的处理没做对。

重点检查：

- transpose
- NZ 或其他布局转换
- scale dtype cast
- packed expert / grouped expert gather
- cache 相关的 dtype 与布局修正

如果这里缺文档，建议直接把它沉淀成固定字段，而不是靠代码阅读补全。

---

## 8. 融合算子支持评估

如果当前模型运行依赖融合算子，量化接入前必须先评估：

- 哪些融合路径支持当前量化方案
- 哪些融合路径不支持
- 是否允许非融合回退

当存在不支持融合算子时，建议把决策固定成三条分支：

1. 接受非融合回退，继续量化接入，同时记录不支持算子
2. 暂不量化，继续做融合适配，同时记录不支持算子
3. 停止优化，回到上游重设计量化方案

这三条决策都应该可追踪地写入 `progress.md` 或等价文档。

---

## 9. 单卡与多卡部署判断

量化接入后，要尽早判断量化是否已经把部署形态改变了。

至少要回答：

- 量化后单卡是否可满足
- 如果单卡可满足，是否可以直接先做单卡验证
- 如果仍需多卡，量化张量是否兼容现有并行切分与 gather 路径

不要默认“量化之后仍完全沿用原并行策略”，这一步必须重新确认。

---

## 10. 最小闭环验证

infer 侧至少要做一次最小闭环，确认“量化路径真的生效”，而不是只把文件读进来了。

建议最小验证包括：

1. 权重成功加载
2. 关键运行对象走到了量化路径
3. prefill / decode 都能跑通
4. 输出数值没有明显异常
5. 回退逻辑可控

如果只是模型能启动，但无法证明走的是量化路径，这个接入不算真正完成。

---

## 11. 通用接入 vs route-specific 接入

接入时建议明确标注是哪一类：

### 通用接入

满足这些条件时，才建议记成 infer 仓的通用量化能力：

- 工件格式稳定
- 运行对象映射稳定
- post-load 规则稳定
- 不依赖特定模型私有 patch

### route-specific 接入

出现这些情况时，更适合标成 route-specific：

- 依赖特定模型脚本或专用转换
- 依赖外部框架 patch
- 运行对象和张量规则只对单个模型成立

不要把 route-specific 结果误写成仓内通用能力，否则后续会反复踩坑。

---

## 12. infer 侧推荐执行顺序

建议按下面顺序推进：

1. 收齐交付物
2. 检查 `config.json`
3. 检查权重索引与量化张量
4. 读 `deploy_quantization.md`
5. 建立 `target -> runtime object` 映射
6. 评估融合算子支持边界
7. 实现 post-load
8. 加载量化权重
9. 跑最小闭环验证
10. 回写兼容性结果与不支持点

这个顺序的价值是：先把“能不能接”判断清楚，再开始改代码。

---

## 13. 一页版结论

如果你时间非常紧，只记住这几句话：

- infer 接入时只依赖交付物，不依赖上游 Python 细节
- 最小交付物是 `config.json`、`model.safetensors.index.json`、`*.safetensors`、`deploy_quantization.md`
- 先把 target 映射成 `Linear / MoEGMM / KVCache`
- 先评估融合支持，再决定是否继续量化改造
- 一定要证明量化路径真实生效，而不是只把文件加载成功
